À lire d’abord

Vous reprenez le code du tableau de bord NC FTO2. Inutile de lire ce manuel d’un bout à l’autre. Lisez ce chapitre : dix minutes. Gardez le chapitre 2 pour le jour où quelque chose ne va pas. Le reste est une référence, à ouvrir à la page utile.

Ce que c’est

Tout le système tient en deux choses : un notebook qui écrit quatre tables, et une application Slate qui les lit. Pas de serveur, pas de base de données propre. Rien ne tourne tout seul, sauf la copie des quatre tables vers la base que lit Slate.

Deux façons de travailler

Dans Skywise seulement. Suffit pour tout ce qui est un paramètre, et pour réparer : lire le message du notebook, corriger une table, remettre le code précédent d’une page. Il faut un navigateur et les droits décrits dans le Access guide.

Avec le dossier source sur un ordinateur. Nécessaire pour modifier le programme ou les pages. Le dossier contient le code, les données d’un jour de référence, et des vérifications qui comparent chaque chiffre des pages avec cette référence : une modification qui fait bouger un chiffre qui ne devait pas bouger est repérée avant d’arriver dans Skywise. Il faut Python 3 et Node.js ; le chapitre 8 explique comment construire et vérifier.

Ce qui n’est pas terminé, et ce qu’il faut savoir

SujetL’état des choses
La cause des nouveaux défautsLa cause de chaque ligne de défaut est stockée dans le dataset fto2_ai_labels. Ces étiquettes ont été faites en deux passes (12 octobre et 4 novembre 2026) par un modèle de langage lisant le texte complet de chaque NC avec les définitions de l’onglet Définitions, suivies de deux passes de relecture. Une ligne écrite ou modifiée depuis est classée par le lecteur de défauts du programme, un ensemble de règles : sur les lignes qui ont les deux, il donne la même catégorie que l’étiquette stockée pour 94 % d’entre elles et la même cause pour 88 %. Rien n’est à faire pour que le tableau de bord reste complet. Chaque exécution écrit les lignes en attente d’étiquette dans fto2_lines_to_label.csv ; les étiqueter à nouveau demande un outil validé par l’informatique pour les textes des NC (chapitre 4).
Le début de chaque annéeLes alarmes comparent les dernières semaines aux semaines d’avant, à l’intérieur de l’année suivie. Tant que l’année n’a pas seize semaines terminées (fin avril), la cloche dit qu’elle n’a pas assez de semaines, et une action MFT commencée dans les premières semaines de l’année n’a pas de référence. C’est voulu ; regarder dans l’année précédente l’éviterait et n’est pas fait.
Les actions MFTLa liste partagée est la table 1_actions_mft.csv. Slate ne donne pas de stockage partagé à un Code Sandbox : une action tapée sur la page reste dans ce navigateur jusqu’à ce que quelqu’un l’ajoute à la table.
L’exécution est manuelleQuelqu’un lance le notebook. Le programme peut aussi tourner comme une transformation planifiée d’un Code Repository (fto2/transform_io.py le prépare) ; cela n’a pas été mis en place.
L’A400MLe texte de ses NC n’est pas disponible dans Skywise : elles comptent comme NC et dans le coût, et aucun défaut n’est lu.
Les aléasL’extrait de MES Disruptions utilisé pour construire le programme s’arrêtait à exactement 2 500 lignes. Si le nombre d’aléas d’une année reste un nombre rond, cherchez une limite sur ce dataset.
Le prix des piècesSeules les pièces dont le prix est saisi dans 1_prix_pieces.csv sont valorisées. Chaque exécution liste les pièces encore à chiffrer dans fto2_parts_to_price.csv.
L’outil de rédaction des NCUne NC est enregistrée en deux clics : Soumettre la NC dans l’outil, puis Submit dans le formulaire de l’action. La clé de l’objet (Timestamp) est un identifiant créé par l’action : l’heure de rédaction de la NC n’est pas conservée. L’outil transmet aussi submission_id, timestamp et defauts_json, que l’action n’utilise pas aujourd’hui.
L’ancienne applicationTant que garder_anciennes_sorties vaut oui dans 2_parametres.csv, le notebook écrit aussi les quatre tables de l’ancienne application Slate. Mettez non une fois cette application retirée.

Quand quelque chose ne va pas

Partez de ce que vous voyez. Chaque ligne renvoie à l’endroit où se trouve le plus souvent la cause. Rien ici ne demande le dossier source : tout se fait dans Skywise.

Le notebook s’arrête

Le notebook vérifie d’abord les paramètres, en moins d’une seconde, avant de lire ou d’écrire quoi que ce soit. Une exécution qui s’arrête là n’a rien changé : le tableau de bord montre toujours l’exécution précédente.

Les chiffres sont anciens

La date Données au… en haut de la page est le jour de la NC la plus récente reçue par la page. Suivez la chaîne de gauche à droite et arrêtez-vous au premier maillon en retard.

  1. Le notebook. Quand a-t-il été lancé pour la dernière fois, et a-t-il atteint ses dernières lignes, la liste des tables écrites ? Sinon : lancez-le, ou voyez la section 2.1.
  2. Les quatre datasets. Ouvrez fto2_dash_nc dans Skywise : sa dernière mise à jour doit être l’heure de l’exécution.
  3. La synchronisation vers Postgres. Dans Slate, exécutez la requête q_fto2_nc et regardez le created le plus récent. Si le dataset est à jour et la requête non, la synchronisation n’a pas tourné : lancez-la, et cherchez pourquoi elle n’a pas suivi la mise à jour.
  4. Le navigateur. Rechargez la page.

Si le notebook a tourné et que les dernières NC manquent toujours, regardez la source : le dataset Non Conformity lui-même est peut-être en retard.

Un chiffre semble faux

Avant d’ouvrir le moindre code, utilisez ce que la page donne.

  1. Est-ce la sélection ? Cliquez sur ⓘ Comment la sélection est faite : la page montre ce que chaque filtre a retiré. La plupart des « totaux faux » s’arrêtent là.
  2. Est-ce une NC ? Retrouvez-la dans la liste en bas de l’onglet. Sa ligne, son produit, son type et sa décision sont le résultat des tables de règles. Pour son coût, Coût de non-qualité › Expliquer le calcul montre chaque étape.
  3. Quelle règle a décidé ? Chaque étiquette d’une NC vient d’une table de règles du groupe 2 (2_regle_…csv) : la première règle qui correspond l’emporte. Le chapitre 3 liste les tables et ce que chacune décide.
  4. Quel code lit une table ? Le fichier lisez_moi.csv des paramètres a une colonne lu_par : le fichier du programme qui lit chaque table. Pour aller d’une table au code qui l’utilise, partez de là.
  5. Est-ce le calcul ? Chapitre 4 pour ce que calcule le notebook ; chapitre 5 pour ce que calcule la page : taux, objectifs, prévisions et alarmes sont calculés dans la page.

Après une réparation

  • Un paramètre a été corrigé : lancez le notebook, rechargez la page, comparez les chiffres clés avec ce que vous attendiez.
  • Du code a été remis ou modifié dans Skywise : notez-le, et reportez la même modification dans le dossier source ; sinon la prochaine installation l’efface.
  • Le programme ou une page a été modifié dans les sources : lancez les vérifications du chapitre 8 avant d’installer.

  5. Chargez le notebook fto2_pipeline_notebook.ipynb à la racine.
  6. Dans le panneau Data du workspace, ajoutez les datasets sous exactement ces noms :

La synchronisation vers Postgres

Slate lit les quatre tables dans Postgres. Synchronisez fto2_dash_nc, fto2_dash_defects, fto2_dash_disruptions et fto2_dash_ref, sous les mêmes noms, schéma foundry_sync. Créez chaque synchronisation après une première exécution du notebook, pour que la table ait ses colonnes. La synchronisation doit suivre chaque exécution : vérifiez dans la requête (section 7.6) que la NC la plus récente est celle de l’exécution.

L’application Slate

  1. Créez une application Slate.
  2. Ajoutez quatre requêtes sur la source postgate-airbus-2, nommées exactement q_fto2_nc, q_fto2_def, q_fto2_dis et q_fto2_ref, chacune avec le texte de son fichier .sql.
  3. La page tableau de bord. Ajoutez un Code Sandbox, toute la largeur, environ 1 400 px de haut. Collez fto2_level23.css, .html et .js dans ses onglets CSS, HTML et JavaScript, et state.json dans sa case d’état : il relie les quatre requêtes à la page.
  4. La page MFT. Sur une deuxième page de l’application, un deuxième Code Sandbox, même taille, avec les fichiers de mft/ et son state.json. Elle utilise q_fto2_nc, q_fto2_def et q_fto2_ref.
  5. Partagez l’application et les quatre datasets avec les lecteurs (le Access guide).
Trois règles pour le code collé dans Slate
  • Jamais deux accolades ouvrantes à la suite dans le JavaScript : Slate les lit comme un lien vers une requête.
  • Chaque règle CSS commence par .fto2, pour que les styles n’atteignent pas le reste de la page Slate.
  • Pas de données dans le code : données et paramètres viennent des requêtes.

L’outil de rédaction des NC

L’outil de rédaction est une page où un opérateur rédige une NC avec les codes officiels ; il construit le texte SAP. Chaque NC est enregistrée comme un objet du type d’objet a30 Nc Writer Dataset, par son action. Le Code Sandbox ne peut rien écrire lui-même : il transmet la NC avec un événement ; l’événement remplit une variable Slate ; l’action lit la variable.

  1. Le Code Sandbox. Sur une troisième page, ajoutez un Code Sandbox nommé w_nc_writer, environ 1 316 px de large et 900 px de haut. Collez nc_writer.html, nc_writer.css et nc_writer.js dans ses onglets. État : {}. Dans son onglet Interaction, Events : ["submit"]. L’écran Nouvelle NC apparaît.
  2. La variable. Dans le panneau Variables, ajoutez v_submission, valeur {}.
  3. L’événement. Dans le panneau Events, ajoutez un événement. Déclencheur : w_nc_writer.submit. Action : v_submission.set. Code : return {{slEventValue}};
  4. L’action. Ajoutez un widget Action avec l’action du type d’objet. Dans ses paramètres par défaut :
    ChampValeur
    Detection"{{v_submission.detection}}"
    Produit"{{v_submission.produit}}"
    Msn"{{v_submission.msn}}"
    Texte Sap"{{v_submission.texte_sap}}"
    Total Defauts{{v_submission.total_defauts}} (un nombre : sans guillemets)
    La clé, Timestamp, est remplie par l’action elle-même.
  5. Vérification. Rédigez une courte NC, appuyez sur Soumettre la NC : l’outil affiche NC prête à enregistrer et le formulaire de l’action montre la NC. Appuyez sur Submit : un nouvel objet existe, avec le MSN saisi. Supprimez ensuite l’objet de test.

Pour vérifier chaque maillon de cette chaîne séparément, le dossier 08_tools/nc_writer_slate/test_action/ contient un petit Code Sandbox de test et les étapes, d’un état saisi à la main jusqu’à l’événement. Les utilisateurs de l’outil ont besoin du droit d’exécuter l’action (le Access guide).

Vérifier l’installation

  • Le tableau de bord s’ouvre en Essentiel. La date Données au… en haut à droite est le jour de la NC la plus récente. Avec les filtres de l’ouverture (Série, Responsabilité FTO2), Deep dive › Vue d’ensemble affiche un peu plus que 868 NC, 3 160 défauts et 388 k€ : ce sont les chiffres du 26 octobre 2026, et la source contient plus de jours.
  • La page MFT s’ouvre sur la ligne qui a le plus de NC, sur la dernière semaine terminée, et Suivi des actions montre les actions de 1_actions_mft.csv.
  • Les requêtes : dans Slate, q_fto2_nc renvoie autant de lignes que le notebook en a écrit dans fto2_dash_nc. Un nombre qui s’arrête à un chiffre rond signale une limite de lignes sur la requête.

Modifier le code et le vérifier

Toute modification du programme ou des pages se fait dans le dossier source, est vérifiée contre une référence, construite, puis installée. Les vérifications comparent chaque chiffre affiché par les pages avec les chiffres d’un jour de référence : une modification qui fait bouger un chiffre qui ne devait pas bouger est vue avant d’arriver à l’équipe.

Ce qu’il faut

  • Python 3 avec les paquets de requirements.txt (pandas, numpy, openpyxl).
  • Node.js avec Playwright et son Chromium : les vérifications ouvrent les pages dans un navigateur.
  • Le dossier source, avec ses données de référence : 06_input_data/ (les extraits d’un jour de référence), 04_reference/, 05_outputs/ (ce qu’écrit la construction) et tests/golden/ (ce que montraient les pages).

Lancez les commandes depuis le dossier source. Python est appelé avec -I, ce qui l’empêche de charger quoi que ce soit depuis le dossier courant.

La seconde fait de même pour la page MFT. Les deux réécrivent FTO2_Skywise_installation.zip.

La règle d’une modification

  1. Notez ce qui doit bouger, et ce qui ne doit pas bouger.
  2. Faites la modification dans le dossier source.
  3. Construisez, puis lancez les vérifications. Lisez chaque différence signalée par la référence des pages.
  4. Si seul ce que vous vouliez a bougé, et qu’un chiffre devait changer : faites de la nouvelle capture la référence (tests/README.md), dans la même modification.
  5. Installez la nouvelle version (section 7.7), et vérifiez les pages dans Skywise.
