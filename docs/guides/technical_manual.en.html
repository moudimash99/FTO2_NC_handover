Read this first

You have taken over the code of the FTO2 NC dashboard. You do not need to read this manual from end to end. Read this chapter: it takes ten minutes. Keep chapter 2 for the day something breaks. The rest is a reference, to open at the page you need.

What it is

The whole system is two things: a notebook that writes four tables, and a Slate application that reads them. There is no server and no database of its own. Nothing runs by itself except the copy of the four tables to the database Slate reads.

Three kinds of things, and where each one lives

WhatWhere it runs in SkywiseWhere its original is
The settings
45 small tables		data/config/ in the Code Workspace. The team changes them there.In Skywise. The folder config of the source is only the starting copy.
The program
Python		notebook_kit/fto2/ in the Code Workspace, run by the notebook.The source folder, fto2/.
The pages

The rule to remember For the program and the pages, Skywise holds copies and the source folder holds the original. A change typed directly into notebook_kit or into a Slate sandbox works, and is lost at the next installation. Make the change in the source, run the checks, build, then install (chapters 7 and 8). For the settings it is the opposite: the original is data/config/ in Skywise. Never upload the folder config of the source over it.

Two ways of working

In Skywise only. Enough for everything that is a setting, and to repair: read the notebook's message, correct a table, put a page's previous code back. You need a browser and the rights of the Access guide.

With the source folder on a computer. Needed to change the program or the pages. The folder holds the code, the data of a reference day, and checks that compare every figure of the pages with that reference: a change that moves a number it should not move is caught before it reaches Skywise. You need Python 3 and Node.js; chapter 8 says how to build and check.

What is not finished, and what to know

SubjectThe state of things
The cause of new defectsThe cause of each defect line is stored in the dataset fto2_ai_labels. These labels were made in two passes (12 October and 4 November 2026) by a language model reading the full text of each NC with the definitions of the tab Définitions, followed by two review passes. A line written or changed since then is classified by the defect reader of the program, a set of rules: on the lines that have both, it gives the same category as the stored label for 94 % of them and the same cause for 88 %. Nothing has to be done for the dashboard to stay complete. Each run writes the lines waiting for a label in fto2_lines_to_label.csv; labelling them again needs a tool approved by IT for the NC texts (chapter 4).
The beginning of each yearThe alarms compare the last weeks with the weeks before, inside the year followed. Until the year has sixteen finished weeks (late April) the bell says that it has not enough weeks, and an MFT action started in the first weeks of the year has no reference. It is by design; looking back into the previous year would remove it and is not done.
The MFT actionsThe shared list is the table 1_actions_mft.csv. Slate gives a code sandbox no shared storage, so an action typed on the page stays in that browser until someone adds it to the table.
The run is manualSomeone runs the notebook. The program can also run as a scheduled transform of a Code Repository (fto2/transform_io.py prepares it); this was not put in place.
The A400MThe text of its NCs is not available in Skywise: they count as NCs and in the cost, and no defect is read.
The aléasThe extract of MES Disruptions used to build the program stopped at exactly 2,500 rows. If the number of aléas of a year stays at a round number, look for a limit on that dataset.
The part pricesOnly the parts whose price is typed in 1_prix_pieces.csv are valued. Each run lists the parts still to price in fto2_parts_to_price.csv.
The NC writerAn NC is saved in two clicks: Soumettre la NC in the writer, then Submit in the action's form. The object's key (Timestamp) is an id made by the action: the time the NC was written is not stored. The writer also hands over submission_id, timestamp and defauts_json, which the action does not use today.
The former applicationWhile garder_anciennes_sorties is oui in 2_parametres.csv, the notebook also writes the four tables of the former Slate application. Set it to non once that application is retired.

When something breaks

Start from what you see. Each row sends you to the place where the cause usually is. Nothing here needs the source folder: everything is done in Skywise.

The notebook stops

The notebook checks the settings first, in less than a second, before it reads or writes anything. A run that stops there has changed nothing: the dashboard still shows the previous run.

The last messageWhat it meansWhat to do
Names a file of data/config/ and a line.A settings table is badly filled: a ; typed in a cell, a date, a word that is not one of the allowed ones.Correct that line. The message says what is expected. Chapter 3, "The basics".
"settings table … not found"A table was renamed, moved or deleted.Put it back in data/config/, from the folder config of the installation.
A dataset name that is not found; or, at the end of the run, an error AliasNotDefined with 'alias': 'fto2_dash_…'.The dataset is not in the Data panel of the workspace under that name. The error lists the names the panel holds (definedAliases).Add it in the Data panel with the name of section 7.2 (a new, empty dataset is fine: the notebook fills it), or change the name in 2_sources.csv. Then run the notebook again.
A permission error on a dataset.The person who runs the notebook lacks access.The Access guide, chapter 5.
"… is not a price"Text in the price column of 1_prix_pieces.csv.Correct that line.
"fto2_dash_cout not written"Normal: that table only serves an optional set-up.Nothing.
A warning ⚠️ at the end, about the year.The clock is in a new year and the settings still follow the previous one.The new-year list of the Settings guide, chapter 7.
Any other error.The last step printed says how far the run went.Chapter 4, "The run, step by step", gives the file of each step.

If the same error comes back after a correction, restart the kernel of the notebook and run every cell again: Python keeps in memory what it has already loaded.

The figures are old

The date Données au… at the top of the page is the day of the latest NC the page received. Follow the chain from left to right and stop at the first link that is late.

  1. The notebook. When was it last run, and did it reach its last lines, the list of the tables written? If not: run it, or see section 2.1.
  2. The four datasets. Open fto2_dash_nc in Skywise: its last update must be the time of the run.
  3. The sync to Postgres. In Slate, run the query q_fto2_nc and look at the most recent created. If the dataset is up to date and the query is not, the sync has not run: start it, and find out why it did not follow the update.
  4. The browser. Reload the page.

If the notebook ran and the latest NCs are still missing, look at the source: the dataset Non Conformity itself may be late.

A figure looks wrong

Before opening any code, use what the page gives.

  1. Is it the selection? Click ⓘ Comment la sélection est faite: the page shows what each filter removed. Most "wrong totals" end here.
  2. Is it one NC? Find it in the list at the bottom of the tab. Its line, product, type and decision are the result of the rule tables. For its cost, Coût de non-qualité › Expliquer le calcul shows every step.
  3. Which rule decided? Each label of an NC comes from one rule table of group 2 (2_regle_…csv): the first rule that matches wins. Chapter 3 lists the tables and what each decides.
  4. Which code reads a table? The file lisez_moi.csv of the settings has a column lu_par: the file of the program that reads each table. From a table to the code that uses it, start there.
  5. Is it the calculation? Chapter 4 for what the notebook computes; chapter 5 for what the page computes: rates, targets, forecasts and alarms are computed in the page.

After a repair

  • A setting was corrected: run the notebook, reload the page, compare the key figures with what you expected.
  • Code was put back or changed in Skywise: note it, and bring the same change into the source folder; otherwise the next installation removes it.
  • The program or a page was changed in the source: run the checks of chapter 8 before installing.

The whole set-up, from nothing, in the order to follow. Allow an hour. The same steps install a new version: section 7.7 says which ones to repeat.

The Code Workspace

  1. Upload the folder notebook_kit at the top of the workspace.
  2. Create a folder data. Upload the folder config into it, so that it becomes data/config. Do this once: from then on, the settings are changed there.
  3. Put the three files of the team in data, under the names of 2_sources.csv, with the downloads if you have them (an export of the plan: a name starting with Avances_Retards; of the cable tracker: a name containing cables).
  4. In data/config/2_parametres.csv, line garder_anciennes_sorties: non if no former application has to be fed; oui writes, in addition, the four tables of the former application (they must then be in the Data panel too).
  5. Upload the notebook fto2_pipeline_notebook.ipynb at the top.
  6. In the Data panel of the workspace, add the datasets under exactly these names:
    DatasetName in the Data panelAccess
    Non Conformitynon_conformityread
    The cause labelsfto2_ai_labelsread
    Work_Order_Operationwork_order_operationread
    MES Disruptionsmes_disruptionsread
    Four new, empty datasetsfto2_dash_nc, fto2_dash_defects, fto2_dash_disruptions, fto2_dash_refwrite
  7. fto2_ai_labels holds 3,489 rows. If it is new or holds fewer, give it the content of notebook_kit/fto2_ai_labels.csv.
  8. Run all the cells. The first lines say the year followed; the last lines list the four tables written, then Done. If the run stops, chapter 2.

The sync to Postgres

Slate reads the four tables from Postgres. Sync fto2_dash_nc, fto2_dash_defects, fto2_dash_disruptions and fto2_dash_ref, under the same names, schema foundry_sync. Create each sync after a first run of the notebook, so that the table has its columns. The sync must follow each run: check in the query (section 7.6) that the most recent NC is the one of the run.

The Slate application

  1. Create a Slate application.
  2. Add four queries on the source postgate-airbus-2, named exactly q_fto2_nc, q_fto2_def, q_fto2_dis and q_fto2_ref, each with the text of its .sql file.
  3. The dashboard page. Add a Code Sandbox, full width, about 1,400 px high. Paste fto2_level23.css, .html and .js into its CSS, HTML and JavaScript tabs, and state.json into its state box: it binds the four queries to the page.
  4. The MFT page. On a second page of the application, a second Code Sandbox, same size, with the files of mft/ and its state.json. It uses q_fto2_nc, q_fto2_def and q_fto2_ref.
  5. Share the application and the four datasets with the readers (the Access guide).
Three rules for code pasted in Slate
  • Never two opening curly braces in a row in the JavaScript: Slate reads them as a link to a query.
  • Every CSS rule starts with .fto2, so that the styles do not reach the rest of the Slate page.
  • No data in the code: data and settings come from the queries.

The NC writer

The NC writer is a page where an operator writes an NC with the official codes; it builds the SAP text. Each NC is saved as an object of the object type a30 Nc Writer Dataset, through its action. The code sandbox cannot write anything itself: it hands the NC over with an event; the event fills a Slate variable; the action reads the variable.

  1. The sandbox. On a third page, add a Code Sandbox named w_nc_writer, about 1,316 px wide and 900 px high. Paste nc_writer.html, nc_writer.css and nc_writer.js into its tabs. State: {}. In its Interaction tab, Events: ["submit"]. The screen Nouvelle NC appears.
  2. The variable. In the Variables panel, add v_submission, value {}.
  3. The event. In the Events panel, add an event. Trigger: w_nc_writer.submit. Action: v_submission.set. Code: return {{slEventValue}};
  4. The action. Add an Action widget with the action of the object type. In its default parameters:
    FieldValue
    Detection"{{v_submission.detection}}"
    Produit"{{v_submission.produit}}"
    Msn"{{v_submission.msn}}"
    Texte Sap"{{v_submission.texte_sap}}"
    Total Defauts{{v_submission.total_defauts}} (a number: no quotes)
    The key, Timestamp, is filled by the action itself.
  5. Check. Write a short NC, press Soumettre la NC: the action's form shows it. Press Submit: a new object exists, with the MSN typed. Delete the test object afterwards.

To check each link of this chain apart, the folder 08_tools/nc_writer_slate/test_action/ holds a small test box and the steps, from a state typed by hand to the event. Users of the NC writer need the right to run the action (the Access guide).

Checking the installation

  • The dashboard opens in Essentiel. The date Données au… at the top right is the day of the latest NC. With the filters as the page opens (Série, Responsabilité FTO2), Deep dive › Vue d’ensemble shows a little more than 868 NC, 3 160 défauts and 388 k€: these are the figures of 26 October 2026, and the source holds more days.
  • The MFT page opens on the line with the most NCs, on the last finished week, and Suivi des actions shows the actions of 1_actions_mft.csv.
  • The queries: in Slate, q_fto2_nc returns as many rows as the notebook wrote in fto2_dash_nc. A count that stops at a round number means a row limit on the query.

Changing the code and checking it

Every change of the program or of the pages is made in the source folder, checked against a reference, built, then installed. The checks compare every figure the pages show with the figures of a reference day: a change that moves a number it should not move is seen before it reaches the team.

What is needed

  • Python 3 with the packages of requirements.txt (pandas, numpy, openpyxl).
  • Node.js with Playwright and its Chromium: the checks open the pages in a browser.
  • The source folder, with its reference data: 06_input_data/ (the extracts of a reference day), 04_reference/, 05_outputs/ (what the build writes) and tests/golden/ (what the pages showed).

Run the commands from the source folder. Python is called with -I, which keeps it from loading anything from the current folder.

Build

python3 -I build/build_all.py
python3 -I 07_scripts/mft/build_mft.py

The first command runs the program on the reference data, writes the tables of 05_outputs/, the dashboard page 03_reports/FTO2_NC_Dashboard.html (it opens in a browser, with the reference data), and the installation files of the dashboard. The second does the same for the MFT page. Both rewrite FTO2_Skywise_installation.zip.

The rule of a change

  1. Note what should move, and what should not.
  2. Make the change in the source folder.
  3. Build, then run the checks. Read every difference the snapshot reports.
  4. If only what you meant has moved, and a figure was meant to change: make the new snapshot the reference (tests/README.md), in the same change.
  5. Install the new version (section 7.7), and check the pages in Skywise.
