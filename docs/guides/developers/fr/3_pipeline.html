Ce que fait la mise à jour

La mise à jour lit les NC dans Skywise, décide lesquelles comptent, lit les défauts écrits dans chaque NC, donne une cause à chaque défaut, calcule le coût, et écrit les quatre tables que lisent les pages. C’est du Python simple, un fichier par sujet (le dossier fto2), et elle tourne de l’une de ces deux façons :

  • Le Code Repository : un transform, fto2_update.py, que Skywise lance selon une planification. Les tables de réglages sont gardées avec le code (fto2/settings).
  • Le notebook du pipeline, dans un Code Workspace, lancé à la main. Les réglages sont dans son dossier data/config.

Les deux font exactement les mêmes étapes et écrivent les mêmes tables. Utilisez l’un ou l’autre, pas les deux : une fois que le transform planifié tourne, le notebook n’est plus utilisé, et le code ne se modifie plus que dans le Code Repository. Deux copies du code qui divergent sont le moyen le plus sûr d’obtenir deux tableaux de bord différents.

Les étapes, dans l’ordre

  1. Réglages. Chaque réglage est lu et vérifié en premier. Une erreur arrête l’exécution ici, avant toute récupération de données. L’arbre des causes de l’onglet Définitions est vérifié par rapport au code, et une fermeture qui manque dans les jours de fermeture est signalée.
  2. Sélection. Les NC créées depuis le 1er janvier de l’année de comparaison sont récupérées (les deux années : les pages choisissent l’année qu’elles montrent), les NC exclues sont laissées de côté, et chaque NC reçoit ses étiquettes des tables de règles : phase (série, REC, FTI), décision, origine, type, produit.
  3. Les listes. Les NC du registre GPS et de la liste Test que la sélection n’a pas trouvées sont récupérées par leur numéro. Elles passent par les mêmes règles d’exclusion, et ne comptent que si elles ont été créées dans l’année suivie.
  4. Défauts. Le lecteur de défauts découpe le texte de chaque NC en lignes de défaut et donne à chacune une sous-catégorie. Les NC A400M n’ont pas de texte dans Skywise : une ligne est faite à partir du titre.
  5. Causes. Chaque ligne de défaut prend son étiquette enregistrée, si son texte n’a pas changé depuis qu’elle a été étiquetée. Un code écrit dans la NC par une personne l’emporte sur l’étiquette : écrit avec la Saisie structurée de NC, le sous-code entier (Q03-006) décide de la ligne ; tapé à la main, le code compte par sa famille (Q03), et une étiquette d’une autre famille lui cède la place. Une ligne sans étiquette utilisable garde la cause du lecteur de défauts et est listée « à étiqueter ».
  6. Coût. Les ordres de retouche, les aléas et les prix des pièces sont rattachés, et le modèle de coût tourne sur chaque NC.
  7. Données de référence. Le plan de production ; les chiffres de l’année de comparaison, additionnés à partir des mêmes NC traitées (les deux années sont donc comptées et chiffrées de la même façon), avec son volume mesuré comme celui de cette année (produits fabriqués, répartis sur les jours ouvrés ; 2025 tiré de sa table de livraisons) ; les demandes de câbles, les actions MFT, l’arbre des causes, les réglages des pages et le poids de travail de chaque jour et de chaque semaine des deux années (tiré des jours de fermeture).
  8. Écriture. Les quatre tables sont écrites, puis synchronisées vers Postgres.

L’exécution affiche chaque étape au fur et à mesure : la dernière ligne affichée dit donc où elle en est.

Le sens de chaque colonne est écrit à côté d’elle, en haut de core.py. Deux fichiers de travail sont aussi écrits à côté du notebook : les lignes à étiqueter, et les pièces encore sans prix.

L’année

L’année suivie est l’année en cours, et l’année de comparaison celle d’avant. La mise à jour lit et écrit les deux années ; les pages filtrent l’année qu’elles montrent (ce qui relève des pages reste dans les pages). Chaque date de l’exécution vient de ces deux années, par quelques petites fonctions de config.py ; aucune année n’est écrite nulle part dans le code. Pour regarder une année passée, écrivez-la sur la ligne annee de 1_parametres.csv ; videz de nouveau la ligne ensuite.

Le modèle de coût, en bref

Chaque NC passe par six étapes au plus : l’alerte, la rédaction de la NC, le support technique, la préparation du travail, l’intervention, et le recontrôle. Chaque étape prend des minutes, comptées au taux horaire de qui la fait. S’y ajoutent les heures d’ingénierie, la matière et le prix d’une pièce rejetée, rebutée ou échangée. La décision (retouche, rebut, demande de DQN…) dit quelles étapes sont comptées. Quand une NC a un ordre de retouche clos avec un temps planifié, ce temps remplace l’estimation du modèle. La description complète, avec les minutes et les taux d’aujourd’hui, se trouve dans Comment le coût est calculé, dans le dossier des utilisateurs ; le code est dans cost/.

Lancer la mise à jour

Dans le Code Repository, c’est la planification qui la lance ; pour la lancer tout de suite, lancez un build de fto2_dash_nc. Son journal affiche les mêmes lignes que le notebook. Dans le notebook, exécutez toutes les cellules, de la première à la dernière. Dans les deux cas :

  1. Lisez les premières lignes : l’année suivie, et les réglages venus de Fusion.
  2. Lisez les dernières lignes : le nombre de NC et de lignes de défaut, les tables écrites, et tout avertissement.
  3. Quelques minutes plus tard, ouvrez le tableau de bord : la date Données au… doit être le jour de la dernière NC.

Une modification du code dans le Code Repository prend effet au build suivant, une fois commitée et vérifiée. Dans le notebook, le code est relu à chaque exécution : inutile de le redémarrer.

Quand la mise à jour s’arrête

Le messageQue faire
Nomme une table de réglages et une ligneCette ligne est mal remplie : corrigez-la, puis relancez.
« settings table … not found »Une table a été renommée ou supprimée : remettez-la.
Un dataset introuvableNotebook : le dataset n’est pas dans le panneau Data (AliasNotDefined). Code Repository : ce n’est pas une entrée du transform. Ajoutez-le, ou changez son nom dans 2_sources.csv.
« the station list is missing »Code Repository : fto2_station_mapping.csv doit être dans fto2/files.
⚠️ Une feuille Fusion « NOT USED »La mise à jour garde la table précédente et dit pourquoi : le plus souvent la ligne d’en-tête n’a pas été trouvée (une colonne manquante ou renommée dans la source). Videz la feuille, recollez toute la source en A1, et relancez.
« fto2_dash_cout not written »Normal : cette table ne sert qu’aux fonctions Slate facultatives.
Une liste « could not be read »Le registre GPS ou la liste Test manque ou a changé de forme : ses NC passent sans les informations de la liste.
Toute autre erreurLa dernière étape affichée dit où elle en était ; c’est dans le fichier de cette étape qu’il faut chercher.
