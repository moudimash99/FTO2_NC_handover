Les pages

Chaque page est une application Slate à part : le tableau de bord, la page MFT et la Saisie structurée de NC. Chacune est un code sandbox Slate en quatre parties : CSS (l’apparence), HTML (le cadre, un emplacement vide par graphique), JS (du JavaScript simple, sans bibliothèque extérieure) et State (les liens vers les requêtes). Les pages ne font que filtrer, additionner et dessiner ; chaque chiffre qu’elles affichent a été décidé par la mise à jour.

Comment une page reçoit ses données

  1. Les requêtes q_fto2_nc, q_fto2_def, q_fto2_dis et q_fto2_ref lisent les quatre tables dans Postgres (schéma foundry_sync). Leur SQL ne fait que lister les colonnes.
  2. Le State du sandbox donne à chaque résultat un nom que la page connaît : nc, def, dis, ref.
  3. Deux requêtes facultatives : q_fto2_set_targets (la feuille Fusion Target and pages, clé reglages du State) sur le tableau de bord et la page MFT, et q_fto2_mft_store (les actions MFT, clé store) sur la page MFT. Leurs lignes s’ajoutent au State à la main. Sans elles, une page marche comme avant : l’objectif et la vue d’ouverture de la dernière mise à jour, les actions MFT gardées dans chaque navigateur.
  4. Le chargeur, tout à la fin du JS, attend que les quatre soient arrivés, puis démarre la page. Si l’un d’eux manque toujours, il affiche un encadré qui le nomme.
  5. Les données de référence arrivent en morceaux ; fto2RefBlocks les recolle en un bloc par page.
  6. L’adaptateur fto2FromTables transforme les tables en listes propres à la page, D.ncs et D.defects, chaque ligne étant une liste de valeurs par position. Les positions y sont listées, à côté de la colonne d’où vient chacune.

Ce qui se passe lors d’un clic

Les filtres sont gardés dans un seul objet, GF. Un changement passe par setGF, qui appelle select() pour faire les listes de NC à l’écran (SEL_NC : tout ce que les filtres gardent ; SER_NC : les NC propres à l’usine ; CLI_NC : les retours clients), puis renderAll() redessine. Un clic sur un graphique passe par l’attribut data-pick de l’élément dessiné ; une infobulle, par data-tip.

Modifier un graphique

  • Où il est placé : V2L liste les cartes de chaque onglet, par clé. Déplacez une clé pour déplacer un graphique ; supprimez-la pour cacher le graphique.
  • Quel code le dessine : une clé en lettres (VT, VN…) est dessinée par la fonction nommée dans V2F ; un nombre, par la fonction donnée dans PSPEC ; une clé qui commence par a:, par RV_ANA. Le plus rapide : cherchez quelques mots du titre du graphique dans le JS ; ils mènent à sa clé.
  • Le modifier : continuez à compter à partir de SEL_NC pour que les filtres s’appliquent, et mettez tout nouveau texte dans STR, dans les deux langues.
  • En ajouter un : copiez la fonction d’un graphique semblable sous une nouvelle clé, ajoutez la clé à V2F, ses titres à GSTR, et la clé à V2L.
  • Téléchargement : chaque carte de graphique reçoit un bouton ⤓ Image qui enregistre le graphique en PNG (pngBtn, pngOf) ; une carte sans graphique le cache. Les NC de la sélection se téléchargent en CSV en bas de chaque onglet (csvOf : ses deux listes de colonnes, courte et complète, les plus utiles d’abord).

Les tables contiennent deux années : l’année de comparaison et l’année suivie. Chaque page choisit ce qu’elle montre : le tableau de bord garde l’année suivie (l’adaptateur laisse le reste de côté), la page MFT garde les deux, pour qu’une semaine, un mois ou une action soit comparé aux semaines d’avant, même au changement d’année. La page ne contient aucune année à elle : les années arrivent avec les réglages, et les textes les écrivent {YEAR} et {PREV}. Les noms y25 et v26 dans le code datent de la première année suivie : lisez-les comme « l’année de comparaison » et « l’année suivie ».

Le calendrier dans les pages

Les pages tirent le temps de travail des jours de fermeture, par les données de référence : le poids de chaque jour et de chaque semaine ISO de l’année. Une semaine sous semaine_faible_moins_de (60 % d’une semaine normale) est une semaine de fermeture, laissée hors des moyennes et des références sur chaque page (calW). Le mois en cours compte la part de son temps de travail déjà écoulée (dayShare), pas celle de ses jours calendaires. Les textes qui nomment le volume de l’an dernier l’écrivent par withYears : « livrés » tant qu’il vient de la table des livraisons 2025, « fabriqués » dès qu’il est mesuré à partir du plan.

La cloche

Ligne par ligne, la cloche compare les défauts des 4 dernières semaines terminées aux 12 semaines d’avant, par avion produit, et sonne quand la hausse est trop forte pour être due au hasard. Elle repère aussi les hausses lentes et les avions qui ont bien plus de NC que d’habitude. Ses réglages sont dans 3_alarmes.csv. La page MFT a sa propre copie du moteur d’alarmes : une modification de l’une doit être faite aussi dans l’autre, sinon les deux pages sonneront différemment.

La page MFT

Elle lit les mêmes tables, par son propre adaptateur, plus simple. La page MFT montre une ligne à la fois : le Pareto de la semaine, l’analyse, et le suivi des actions MFT.

La page MFT a la liste Responsabilité du tableau de bord : chaque NC reçoit un groupe tiré de la table (FTO2 quand la NC est imputée à FTO2, Fournisseurs quand sa responsabilité est un numéro de fournisseur, Autres pour le reste), et chaque compte, chaque graphique et la cloche suivent les groupes cochés. Avec la clé store, les actions MFT sont gardées dans un objet du type d’objet de la Saisie structurée de NC (son Msn vaut MFT-ACTIONS, son Texte Sap la liste entière en JSON) : un changement envoie l’événement save avec toute la liste, le changement de la variable soumet le widget Action (un clic), et la page prend l’objet enregistré en dernier. La relecture des enregistrements n’est pas encore réglée (Limites connues et travail en cours).

La Saisie structurée de NC

La Saisie structurée de NC est une page à part, qui aide à rédiger une NC selon le standard. Quand le texte est prêt, elle remplit une variable Slate au moyen d’un événement, et l’action du type d’objet a30 Nc Writer Dataset l’enregistre avec les valeurs de cette variable. Ses listes (produits, défauts, causes) sont en haut de son JS, dans un seul objet de réglages.

Trois règles pour le code dans Slate

  • Jamais deux { à la suite dans le JS. Slate les lit comme un lien vers une requête et casse le code.
  • Chaque règle CSS commence par .fto2, pour que les styles restent dans le sandbox.
  • Pas de données dans le code. Une liste ou une valeur que quelqu’un peut vouloir changer a sa place dans un réglage, lu par la mise à jour et passé à la page.

Avant toute modification, copiez le JS actuel hors du sandbox et gardez-le : c’est votre moyen de revenir en arrière. L’éditeur de Slate est lent avec un fichier aussi long ; modifiez-le dans un éditeur de texte et recollez-le.

Quand une page affiche un encadré

L’encadré ditOù regarder
Toujours en attente d’une requête, avec son nomLe nom et le SQL de la requête dans Slate
La requête n’a renvoyé aucune ligneLa synchronisation, puis la dernière exécution de la mise à jour
Aucune NC lisible, avec les colonnes reçuesLa requête renvoie des colonnes que la page n’attend pas : comparez avec la table
Exactement N lignes reçuesUne limite de lignes sur la requête : Slate a coupé le résultat
Les actions partagées ne sont pas encore lues (page MFT)La requête q_fto2_mft_store : sa table et le nom de ses colonnes
Une erreur avec une ligne de codeLe JS contient une erreur : recollez la version précédente

Une page vide, sans aucun encadré, est en général un problème de droits : la personne peut ouvrir l’application mais pas les quatre tables (Skywise : accès et propriété).
