La chaîne d’un coup d’œil

Le tableau de bord vit entièrement dans Skywise. Ce n’est pas un seul objet, mais une chaîne : les données vont des datasets sources, par la mise à jour, jusqu’à trois applications Slate. Chaque maillon est dans le projet de l’équipe, jamais dans un dossier personnel. Chaque maillon a son chapitre dans ce guide.

La mise à jour dans le Code Repository

La mise à jour est un seul transform Python, dans un Code Repository du projet de l’équipe. C’est un transform léger (lightweight) : du Python simple avec pandas et polars, sans Spark. Un seul build lit toutes les sources et tous les réglages, et écrit les six tables.

Ce que contient le repository

Dans le repositoryCe que c’est

src/fto2/Le code, un fichier par sujet. skywise.py lance les étapes dans l’ordre ; transform_io.py les relie au transform.
src/fto2/settings/Les tables de règles (section 2.3).
src/fto2/files/La liste des postes fto2_station_mapping.csv, et les exports du plan de production, nommés Avances_Retards_<date>.csv. Le plus récent est lu ; les anciens sont gardés.

Le transform et son paquet

  • Entrées : les quatre datasets sources, par leur identifiant ; les six datasets Fusion que lit la mise à jour, par leur chemin (le dossier Fusion Sheets, puis FTO2 NC Dashboard - Settings - <feuille>).
  • Sorties : les six tables, dans le dossier Datasets.
  • Les lignes du haut : FOLDER, le dossier où les tables sont écrites ; FUSION, le dossier Fusion Sheets qu’il contient ; TEST.
  • TEST = "_test" écrit des tables à part (fto2_dash_nc_test…), pour un premier essai. TEST = "" écrit les tables que lisent les pages.
  • Aucune ligne de ce fichier ne doit dépasser 120 caractères (chapitre 7).

La recette conda, conda_recipe/meta.yaml, liste sous run: les trois bibliothèques dont le code a besoin, avec le même retrait que les lignes au-dessus :

    - pandas
    - pyarrow
    - polars

src/setup.py garde les tables de réglages et les fichiers avec le code. Après la ligne install_requires=[], il contient :

package_data={"fto2": ["settings/*", "files/*"]},

Sans cette ligne, le build ne trouve pas les tables de réglages.

Le type d’objet

Dans Ontology Manager, le type d’objet a30 Nc Writer Dataset contient un objet par enregistrement. Ses propriétés : Timestamp (la clé, remplie par l’action), Detection, Produit, Msn, Texte Sap et Total Defauts. Son action, Create or Modify a30 Nc Writer Dataset, écrit dans un dataset à elle. Ontology Manager montre aussi les noms d’API du type d’objet et de ses propriétés.

L’enregistrement partagé de la page MFT n’est pas encore utilisé

Reste à régler

Les pièces de la section 5.3, pour la page MFT, sont en place, mais la relecture des enregistrements n’est pas réglée. Deux chemins ont été essayés :

  • Par Postgres : le dataset du type d’objet synchronisé sous le nom fto2_mft_store. Cette copie a du retard sur l’Ontologie : la page ne voit pas un enregistrement au moment où il est fait.
  • Directement dans l’Ontologie : la requête q_fto2_mft_store sur la source HTTP « foundry » de Slate, qui cherche les objets dont le Msn vaut MFT-ACTIONS. Elle n’a pas atteint l’API des objets.

L’enregistrement partagé n’est donc pas utilisé. Les actions MFT que tout le monde voit sont celles de la table 1_actions_mft.csv du Code Repository : une action ajoutée là apparaît après le build suivant. Une action modifiée sur la page elle-même n’est pas gardée. La cloche du tableau de bord ne connaît que les actions de la table.

Reconstruire une partie

Avant de commencer :

  • Souvent, rien n’est à reconstruire. Une version antérieure tirée de l’historique (section 1.2) suffit : l’historique des versions de l’application, les commits du repository, les versions antérieures d’un dataset.
  • Une partie à la fois. Gardez l’ancienne jusqu’à ce que la nouvelle marche.
  • Prenez le code dans Skywise : dans la partie telle qu’elle est, ou dans une version antérieure de son historique.
  • Copiez chaque morceau en entier. Un long texte collé peut perdre sa fin. Comparez ses dernières lignes avec l’original avant d’enregistrer.
  • Gardez exactement chaque nom de la section 1.3.

Une application Slate

  1. Dans le dossier de l’équipe, créez une nouvelle application Slate. Gardez l’ancienne ouverte à côté.
  2. Pour chaque requête de la page (section 5.1) : panneau Queries, +, source postgate-airbus-2, le nom exact, et le texte copié de l’ancienne requête. Appuyez sur Test : elle renvoie des lignes.
  3. Ajoutez un code sandbox (Widgets › Advanced › Code Sandbox). Donnez-lui la taille et le nom de la section 5.1.
  4. Ouvrez l’ancien code sandbox, ou la version qui marchait dans l’historique des versions de l’application. Copiez chaque onglet en entier dans le même onglet du nouveau : CSS, HTML, JS, State. Laissez Libraries vide.
  5. Vérifiez la fin du JS : la page démarre par du code tout à la fin, donc un JS coupé n’affiche rien.
  6. Pour la page MFT et la Saisie structurée de NC, ajoutez l’événement du sandbox, la variable, le widget Action et les événements (section 6.2).
  7. Prévisualisez. Le tableau de bord affiche la date Données au… de la dernière NC. La page MFT s’ouvre sur la ligne qui a le plus de NC, sur la dernière semaine complète, avec Responsabilité FTO2. La Saisie structurée de NC affiche Nouvelle NC.
  8. Partagez la nouvelle application avec les lecteurs (lecture), donnez-leur son lien, puis retirez l’ancienne.

Le Code Repository et sa planification

Essayez d’abord le même repository : son historique garde chaque version antérieure de chaque fichier. Remettez dans le fichier la version qui marchait, commitez, lancez le build. Un nouveau repository n’est utile que si l’ancien est perdu.

  1. Ouvrez le projet de l’équipe, celui qui contient le dossier Datasets. New › Code repository, Python transforms. Un repository n’écrit des tables que dans son propre projet.
  2. Supprimez le transform d’exemple créé par le modèle, dans src/myproject/datasets.
  3. Créez les dossiers src/fto2, src/fto2/settings et src/fto2/files, avec les mêmes fichiers que l’ancien repository, sous les mêmes noms. Copiez le contenu de chaque fichier en entier, depuis l’ancien repository ou son historique. Vérifiez les dernières lignes de chacun.
  4. Créez src/myproject/datasets/fto2_update.py de la même façon. Vérifiez les lignes FOLDER et FUSION : copiez le chemin d’un dossier depuis Skywise plutôt que de le taper. Mettez TEST = "_test".
  5. Dans conda_recipe/meta.yaml, sous run:, ajoutez pandas, pyarrow et polars (section 3.2).
  6. Dans src/setup.py, après install_requires=[],, ajoutez la ligne package_data (section 3.2).
  7. Commitez, et attendez que l’onglet Checks soit vert. Si la vérification de style refuse des lignes de fto2 : dans src/setup.cfg, ajoutez exclude = fto2 sous [flake8] et sous [pycodestyle] ; dans src/.pylintrc, sous [MASTER], ajoutez ignore=fto2. Commitez de nouveau.
  8. Avec fto2_update.py à l’écran, appuyez sur Build et choisissez fto2_dash_nc_test. Lisez le journal (section 3.4). Ouvrez fto2_dash_nc_test : il contient les NC de cette année et de l’année passée.
  9. Mettez TEST = "", commitez, et lancez le build de fto2_dash_nc.
  10. Posez la planification sur le fto2_dash_nc du nouveau repository (ci-dessous), et supprimez l’ancienne planification.

  4. Si Skywise le propose, faites-la tourner pour le projet plutôt que sous une personne. Sinon, prenez un compte qui reste. Cochez la notification en cas d’échec.
  5. Nommez-la FTO2 NC dashboard - daily update, et enregistrez.
  6. Le lendemain matin : le build apparaît dans l’historique des Builds, et la date Données au… du tableau de bord a avancé.

Le classeur Fusion et sa synchronisation

Si une seule feuille a été vidée par erreur, son dernier contenu est dans les versions antérieures de son dataset. Reconstruisez tout le classeur seulement s’il est perdu.

  1. Dans le dossier de l’équipe, créez le classeur FTO2 NC Dashboard - Settings, avec sept feuilles nommées exactement comme dans la section 2.2.
  2. Les quatre feuilles remplies à la main : sur la première ligne, les colonnes de la section 2.3. Puis les valeurs, depuis la dernière version du dataset de la feuille, ou depuis sa table dans src/fto2/settings/.
  3. Les trois feuilles collées entières : collez la source actuelle à partir de la cellule A1, en entier, telle quelle.
  4. Synchronisez chaque feuille vers un dataset du dossier Fusion Sheets. Gardez le nom que donne Fusion : FTO2 NC Dashboard - Settings - <feuille>.
  5. Synchronisez FTO2 NC Dashboard - Settings - Target and pages vers Postgres, sous le nom fto2_set_targets (section suivante).
  6. Lancez le build de fto2_dash_nc, ou attendez la planification. Les premières lignes du journal disent quels réglages viennent de Fusion, et sur quelle ligne a été trouvé l’en-tête de chaque feuille collée entière.

Un dataset sous un autre nom ou dans un autre dossier n’est pas trouvé par le transform. Rendez-lui son nom et son dossier, ou écrivez son identifiant (Copy RID) à la place de son chemin dans le transform.

Les synchronisations Postgres

  1. Ouvrez le dataset, puis ses synchronisations. Ajoutez une synchronisation Postgres avec les mêmes réglages que celles des autres tables : la même base, le schéma foundry_sync, le nom de table de la section 4.2.
  2. Lancez-la une fois. Dans Slate, testez la requête qui la lit : elle renvoie des lignes.
  3. Quand une table gagne une colonne, lancez sa synchronisation, puis ajoutez la colonne à sa requête.

Les pages ne voient un nouveau build qu’une fois sa synchronisation passée.
