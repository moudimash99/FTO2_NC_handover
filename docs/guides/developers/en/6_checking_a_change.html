The principle

A change should move what it was meant to move, and nothing else. The only way to know is to look at the same figures before and after. It takes ten minutes, and it is the check that catches most mistakes.

Before the change

  1. Note the last lines the update printed: the number of NCs, of defect lines, and the cost.
  2. On the dashboard, with the filters as the page opens, note the four key figures of Essential › Summary: NCs since January, NCs per MSN, cost of non-quality, customer returns. Note one line's figures too.
  3. Keep a copy of what you are about to change: the code file, the table, or the page's JS. It is your way back.

After the change

  1. Run the update, and read its first and last lines.
  2. Compare with your notes. Only what you meant to change should move. A setting that should change one line's target must not change another line's count.
  3. For a page change: open the page in both languages, in Essential and in Deep dive, with a few filters, and open the chart you changed with ⤢ Enlarge. Check the MFT page too when the change touches the bell or the tables.
  4. If something moved that should not have, put the copy back and run again before looking further.

What to check, by kind of change

ChangeWhat to look at
A Fusion sheetThe first lines of the update: the sheet is listed as used. Then the figure it feeds (a target, a cost, a month's volume).
A rule tableThe ⓘ panel under the filters, How the selection is made: how many NCs each filter keeps, before and after.
The defect readerThe number of defect lines, and the Pareto by cause on one line. A small change to the reader can move hundreds of lines.
The cost modelThe cost of one NC with Explain the calculation, step by step, then the total.
A chartThe same count from another chart or tab: two charts of the same thing must agree.
The bellThe list of the bell on the dashboard and on the MFT page: they must ring the same.

The automatic checks

The Code Repository runs its checks at each commit: the code must load, and the transform file must pass the style check (no line over 120 characters). A commit with a red check is not built. After a change of the code, build once by hand and read the update's first and last lines before the schedule runs it.

In the Code Repository

  • When you replace a whole file, check that it is whole. A long text pasted can lose its end, and the build then fails far from the cause (a module "has no attribute"): check the file's last lines before you commit.
  • No line over 120 characters in the transform file. The style check refuses it, and every build then says No transforms discovered.
  • Press Build with the transform file on screen. Build builds the file shown; from any other file it finds nothing to build.

Three habits

  • One change at a time. Two changes made together cannot be told apart afterwards.
  • Write down why. A line in the table's comment column, or a comment above the code, says why the rule exists. The next person will want to remove it otherwise.
  • Tell the users when a figure moves for a reason. A target that changes overnight with no word loses their trust in the dashboard faster than a mistake.
