The chain at a glance

The dashboard lives entirely in Skywise. It is not one object but a chain: the data flows from the source datasets, through the update, to three Slate applications. Every link sits in the team's project, never in a personal folder. Each link has a chapter of its own in this guide.

The update in the Code Repository

The update is one Python transform in a Code Repository of the team's project. It is a lightweight transform: plain Python with pandas and polars, no Spark. One build reads every source and every setting, and writes the six tables.

What the repository holds

In the repositoryWhat it is
src/myproject/datasets/fto2_update.pyThe transform: its inputs, its outputs and the folder lines at its top. It hands everything to the code.
src/fto2/The code, one file per subject. skywise.py runs the steps in order; transform_io.py links them to the transform.
src/fto2/settings/The rule tables (section 2.3).
src/fto2/files/The station list fto2_station_mapping.csv, and the production plan's exports, named Avances_Retards_<date>.csv. The newest is read; the older ones are kept.
conda_recipe/meta.yamlThe libraries the code needs (section 3.2).
src/setup.pyKeeps the settings and the files inside the package (section 3.2).
src/setup.cfg, src/.pylintrcThe style checks run at each commit.

The transform and its package

  • Inputs: the four source datasets, by their id; the six Fusion datasets the update reads, by their path (the folder Fusion Sheets, then FTO2 NC Dashboard - Settings - <sheet>).
  • Outputs: the six tables, in the folder Datasets.
  • The lines at its top: FOLDER, the folder where the tables are written; FUSION, the folder Fusion Sheets inside it; TEST.
  • TEST = "_test" writes tables of their own (fto2_dash_nc_test…), for a first try. TEST = "" writes the tables the pages read.
  • No line of this file may pass 120 characters (chapter 7).

The conda recipe, conda_recipe/meta.yaml, lists under run: the three libraries the code needs, indented as the lines above them:

    - pandas
    - pyarrow
    - polars

src/setup.py keeps the settings tables and the files with the code. After the line install_requires=[], it holds:

package_data={"fto2": ["settings/*", "files/*"]},

Without this line, the build does not find the settings tables.

The schedule

The update runs on a time-based schedule, set on the dataset fto2_dash_nc. One build of that dataset writes all six tables.

SettingValue
TriggerA time, early enough that the tables are fresh when the team opens the pages (for example each working day before the shift). Check the time set in the schedule itself.
Targetfto2_dash_nc alone, not what is upstream: the source data belongs to other teams.
Runs asThe project (its service account), if Skywise offers it; otherwise an account that stays. A schedule runs with its owner's rights, and stops with the owner's account.
On failureA notification to the owner.
NameFTO2 NC dashboard - daily update

Reading a build's log

  1. The first lines: the year followed and the comparison year; Settings from Fusion, the sheets that were read; one line for each sheet pasted whole (Fusion sheet GPS register: header on row 4, … rows). A line starting with ⚠️ names a sheet that was not used, and why.
  2. The last lines: the counts, the tables written, and the warnings again.
  3. A few minutes after the sync: the dashboard's date Données au… is the day of the latest NC.

The object type

In Ontology Manager, the object type a30 Nc Writer Dataset holds one object per save. Its properties: Timestamp (the key, filled by the action), Detection, Produit, Msn, Texte Sap and Total Defauts. Its action, Create or Modify a30 Nc Writer Dataset, writes to a dataset of its own. Ontology Manager also shows the API names of the object type and of its properties.

The shared MFT save is not in use yet

Not settled

The parts of section 5.3, for the MFT page, are built, but reading the saves back is not settled. Two ways were tried:

  • Through Postgres: the object type's dataset synced as fto2_mft_store. That copy lags behind the Ontology, so the page does not see a save when it is made.
  • Straight from the Ontology: the query q_fto2_mft_store on Slate's "foundry" HTTP source, searching the objects whose Msn is MFT-ACTIONS. It did not reach the objects API.

So the shared save is not in use. The MFT actions everyone sees are those of the table 1_actions_mft.csv in the Code Repository: an action added there shows after the next build. An action changed on the page itself is not kept. The dashboard's bell knows only the actions of the table.

To rebuild a part

Before you start:

  • Often, nothing needs rebuilding. An earlier version from the history (section 1.2) is enough: the application's version history, the repository's commits, the earlier versions of a dataset.
  • One part at a time. Keep the old one until the new one works.
  • Take the code from Skywise: from the part as it is, or from an earlier version in its history.
  • Copy each piece whole. A long text pasted can lose its end. Compare its last lines with the original before you save.
  • Keep every name of section 1.3, exactly.

A Slate application

  1. In the team's folder, create a new Slate application. Keep the old one open beside it.
  2. For each query of the page (section 5.1): Queries panel, +, source postgate-airbus-2, the exact name, and the text copied from the old query. Press Test: it returns rows.
  3. Add a code sandbox (Widgets › Advanced › Code Sandbox). Give it the size and the name of section 5.1.
  4. Open the old code sandbox, or the version that worked in the application's version history. Copy each tab whole into the same tab of the new one: CSS, HTML, JS, State. Leave Libraries empty.
  5. Check the end of the JS: the page starts from code at its very end, so a JS cut short shows nothing.
  6. For the MFT page and the NC writer, add the sandbox event, the variable, the Action widget and the events (section 6.2).
  7. Preview. The dashboard shows the date Données au… of the latest NC. The MFT page opens on the line with the most NCs, on the last full week, with Responsabilité FTO2. The NC writer shows Nouvelle NC.
  8. Share the new application with the readers (view), give them its link, then retire the old one.

The saves of the MFT page and the NC writer

The MFT page

  1. In w_fto2_mft, Interaction tab, Events: ["save"].
  2. Variables panel, +: v_mft_store, value {}.
  3. Events panel, +: trigger w_fto2_mft.save, action v_mft_store.set, code return {{slEventValue}};
  4. Under the page, add an Action widget with the action Create or Modify a30 Nc Writer Dataset. Give its default parameters the values of section 5.3. Leave Timestamp empty.
  5. Events panel, +: trigger v_mft_store changed, action the Action widget's Submit. No code.
  6. Events panel, +: trigger the Action widget's submit succeeded, action run q_fto2_mft_store. No code.
  7. Check, once reading back is settled: change an action's weekly point. The grey note Enregistrement… shows, then goes. Ontology Manager shows an object with the Msn MFT-ACTIONS. After a reload, the change is still there.

The NC writer

  1. In w_nc_writer, Interaction tab, Events: ["submit"]. Its State: {}.
  2. Variables panel, +: v_submission, value {}.
  3. Events panel, +: trigger w_nc_writer.submit, action v_submission.set, code return {{slEventValue}};
  4. Add an Action widget with the action of a30 Nc Writer Dataset. Bind its fields to v_submission as in section 5.3.
  5. Events panel, +: trigger v_submission changed, action the Action widget's Submit. No code.
  6. Check: write a test NC with two defects and press Soumettre la NC. The page says NC envoyée, and a new object exists with the MSN typed.

The Code Repository and its schedule

First try the same repository: its history holds every earlier version of each file. Copy the version that worked back into the file, commit, build. A new repository is needed only if the old one is lost.

  1. Open the team's project, the one that holds the folder Datasets. New › Code repository, Python transforms. A repository writes tables only inside its own project.
  2. Delete the example transform the template made, in src/myproject/datasets.
  3. Make the folders src/fto2, src/fto2/settings and src/fto2/files, with the same files as the old repository, under the same names. Copy each file's content whole, from the old repository or its history. Check the last lines of each.
  4. Make src/myproject/datasets/fto2_update.py the same way. Check the lines FOLDER and FUSION: copy a folder's path from Skywise rather than type it. Set TEST = "_test".
  5. In conda_recipe/meta.yaml, under run:, add pandas, pyarrow and polars (section 3.2).
  6. In src/setup.py, after install_requires=[],, add the line package_data (section 3.2).
  7. Commit, and wait until the Checks tab is green. If the style check refuses lines of fto2: in src/setup.cfg, add exclude = fto2 under [flake8] and under [pycodestyle]; in src/.pylintrc, under [MASTER], add ignore=fto2. Commit again.
  8. With fto2_update.py on screen, press Build and choose fto2_dash_nc_test. Read the log (section 3.4). Open fto2_dash_nc_test: it holds this year's NCs and last year's.
  9. Set TEST = "", commit, and build fto2_dash_nc.
  10. Put the schedule on the new repository's fto2_dash_nc (below), and delete the old schedule.

The schedule

  1. Open the dataset fto2_dash_nc, then Schedules (or select it in Data Lineage and open the Schedules panel). Create a new schedule.
  2. Trigger: a time, for example each working day before the shift, time zone Europe/Paris.
  3. Target: fto2_dash_nc alone, not what is upstream.
  4. If Skywise offers it, make it run for the project rather than as a person. Otherwise use an account that stays. Tick the notification on failure.
  5. Name it FTO2 NC dashboard - daily update, and save.
  6. The next morning: the build shows in the Builds history, and the dashboard's date Données au… has moved.

The Fusion spreadsheet and its sync

If only one sheet was emptied by mistake, its last content is in the earlier versions of its dataset. Rebuild the whole spreadsheet only if it is lost.

  1. In the team's folder, create the spreadsheet FTO2 NC Dashboard - Settings, with seven sheets named exactly as in section 2.2.
  2. The four sheets filled by hand: in the first row, the columns of section 2.3. Then the values, from the last version of the sheet's dataset, or from its table in src/fto2/settings/.
  3. The three sheets pasted whole: paste the current source from cell A1, whole, as it is.
  4. Sync each sheet to a dataset in the folder Fusion Sheets. Keep the name Fusion gives: FTO2 NC Dashboard - Settings - <sheet>.
  5. Sync FTO2 NC Dashboard - Settings - Target and pages to Postgres, as fto2_set_targets (next section).
  6. Build fto2_dash_nc, or wait for the schedule. The first lines of the log say which settings came from Fusion, and on which row the header of each sheet pasted whole was found.

A dataset under another name or in another folder is not found by the transform. Give it back its name and folder, or write its id (Copy RID) in place of its path in the transform.

The Postgres syncs

  1. Open the dataset, then its syncs. Add a Postgres sync with the same settings as the syncs of the other tables: the same database, the schema foundry_sync, the table name of section 4.2.
  2. Run it once. In Slate, test the query that reads it: it returns rows.
  3. When a table gains a column, run its sync, then add the column to its query.

The pages see a new build only once its sync has run.
