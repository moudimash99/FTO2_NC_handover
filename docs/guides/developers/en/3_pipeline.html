What the update does

The update reads the NCs from Skywise, decides which ones count, reads the defects written in each NC, gives each defect a cause, works out the cost, and writes the four tables the pages read. It is plain Python, one file per subject (the folder fto2), and it runs in one of two ways:

  • The Code Repository: a transform, fto2_update.py, that Skywise runs on a schedule. The settings tables are kept with the code (fto2/settings).
  • The pipeline notebook, in a Code Workspace, run by hand. The settings are in its data/config folder.

Both run exactly the same steps and write the same tables. Use one, not both: once the scheduled transform runs, the notebook is no longer used, and the code is changed in the repository only. Two copies of the code that drift apart are the surest way to get two different dashboards.

The steps, in order

  1. Settings. Every setting is read and checked first. A mistake stops the run here, before anything is fetched. The cause tree of the Definitions tab is checked against the code, and a missing closure in the blackout days is reported.
  2. Selection. The NCs created this year are fetched, the excluded ones are left out, and each NC gets its labels from the rule tables: phase (series, REC, FTI), decision, origin, type, product.
  3. The lists. The NCs of the GPS register and the Test list that the selection missed are fetched by number. They go through the same exclusion rules, and count only when created in the year followed.
  4. Defects. The defect reader splits each NC's text into defect lines and gives each one a sub-category. A400M NCs have no text in Skywise: one line is made from the title.
  5. Causes. Each defect line takes its stored label, if its text has not changed since it was labelled. An official sub-code written in the NC by a person always wins over the label. A line with no usable label keeps the reader's own cause and is listed "to label".
  6. Cost. Rework orders, aléas and part prices are attached, and the cost model runs on every NC.
  7. Reference data. The production plan, the comparison year (its NCs go through the same steps, then are summed per month; its volume is measured as this year's: products built over the working days, except 2025, from its deliveries table), the cable requests, the MFT actions, the cause tree, the page settings and the working weight of each day and week of the year (from the blackout days).
  8. Writing. The four tables are written, then synced to Postgres.

The run prints each step as it goes, so the last line printed says where it is.

The four tables

TableOne row per
fto2_dash_ncNC: dates, line, plant, liability, cost and its steps, phase, MSN, product, station, type, source.
fto2_dash_defectsDefect line: category, cause, sub-category, cable or not, share of the NC's cost, text, sub-code, FIN, where its cause comes from.
fto2_dash_disruptionsQuality aléa that led to no NC.
fto2_dash_refPiece of text. The reference data is one large block per page, cut into pieces because a cell cannot hold it all; the pages glue the pieces back together.

The meaning of every column is written next to it at the top of core.py. Two working files are also written beside the notebook: the lines to label, and the parts still to price.

The year

The year followed is the current year, and the comparison year the one before. Every date of the run comes from these two, through five small functions of config.py; no year is written anywhere in the code. To look back at a past year, write it on the line annee of 1_parametres.csv; empty the line again afterwards.

The cost model, in short

Each NC goes through up to six steps: the alert, writing the NC, technical support, preparing the job, the hands-on work, and the re-check. Each step takes minutes, paid at the hourly rate of whoever does it. Engineering hours, material and the price of a rejected, scrapped or exchanged part are added. The decision (rework, scrap, design query…) says which steps are charged. When an NC has a closed rework order with a planned time, that time replaces the model's own estimate. The full description, with today's minutes and rates, is How the cost is calculated in the users' folder; the code is in cost/.

Running the update

In the Code Repository, the schedule runs it; to run it at once, build fto2_dash_nc. Its log prints the same lines as the notebook. In the notebook, run every cell from the first to the last. Either way:

  1. Read the first lines: the year followed, and which settings came from Fusion.
  2. Read the last lines: the number of NCs and defect lines, the tables written, and any warning.
  3. A few minutes later, open the dashboard: the date Données au… must be the day of the latest NC.

A change of code in the repository takes effect at the next build, once committed and checked. In the notebook, the code is read again at every run: there is no need to restart it.

When the update stops

The messageWhat to do
Names a settings table and a lineThat line is badly filled: fix it, run again.
"settings table … not found"A table was renamed or deleted: put it back.
A dataset that is not foundNotebook: the dataset is not in the Data panel (AliasNotDefined). Repository: it is not an input of the transform. Add it, or change its name in 2_sources.csv.
"the station list is missing"Repository: fto2_station_mapping.csv must be in fto2/files.
A Fusion sheet "not used"Not an error: the file is used instead. Fix the sheet's column names.
"fto2_dash_cout not written"Normal: that table only serves an optional set-up.
A list "could not be read"The GPS register or the Test list is missing or changed shape: its NCs run without the list's information.
Any other errorThe last step printed says where it was; the file of that step is where to look.
